# Research: Support requests

| # | Decision | Rationale | Rejected |
| --- | --- | --- | --- |
| R1 | Four tables: `support_requests`, `support_messages`, `support_attachments`, `support_status_changes`. | One concept per table; the status history and the thread have different readers and lifetimes. | Status history as a JSON column: cannot be filtered or ordered. |
| R2 | A message stores `author_name` beside a nullable `author_user_id`. | An administrator whose access is withdrawn, or a deleted user, still signs their old replies (principle VIII). | Joining the user every time: the name disappears with the row. |
| R3 | Attachments are their own model, stored under `support/{account_id}/`, and do not touch `storage_used_in_bytes`. | A free account at its storage limit is the account most likely to need help, and must still send a screenshot. `File` always counts against the quota and belongs to fields, life events and groups only. | Reusing `App\Models\File` through `CreateFile`: it refuses with `NotEnoughStorageLeft`. |
| R4 | Attachments are not behind the `file-upload` flag. | That flag guards file fields in vaults, a capability still being built. Support attachments are another capability. | Gating them: support would ship without screenshots wherever the flag is off. |
| R5 | The request number is a stored, unique, random six digit integer shown as `MON-{number}`. Routes and the API address a request by uuid. | `HasUuids` forbids anything sequential leaving the application: the row id would tell how many requests the instance holds. Search accepts the number. | `MON-{id}`: sequential. |
| R6 | Three statuses in `SupportRequestStatusEnum`: `to_handle`, `waiting_on_user`, `solved`, each with an administrator label and a user label. | FR-003 gives one state two wordings; one enum keeps them from drifting apart. | Separate user and admin statuses: two state machines for one fact. |
| R7 | Transitions live in the actions. A user message moves to `to_handle`; an administrator may move anywhere; a reply moves to the status chosen with it; a note never moves. "Already solved" is `SupportRequestPolicy::solve`, asked by the action and the screen. | The screen offers Mark as solved and the action refuses it: a rule stated twice, which `policies.md` puts in a policy. | A bespoke exception: `policies.md` forbids one. |
| R8 | Every administrator action calls `$user->isAdministrator()` and throws `ModelNotFoundException` otherwise, besides the `administrator` middleware. | The API, MCP and the web reach the same action; the action must refuse on its own, and refusing as not found matches `AdminAccessTest`. | Middleware only: MCP tools have no route middleware. |
| R9 | Admin API endpoints and admin MCP tools require a new key scope, `ApiKeyScopeEnum::Administration`, on top of being an administrator. | A key created for a phone's address book must not carry the power to answer every account's requests. Same reasoning as `SensitiveFields`. | Administrator status alone: any leaked key of an administrator would read every request on the instance. |
| R10 | Category copy (label, short label, icon, heading, quote, paragraphs, subject hint) lives on `SupportCategoryEnum`, which implements `Translatable`. | Five fixed categories; the copy moves with them and `monica:localize` finds it, as with `ApiKeyScopeEnum`. | A config file: not seen by the localize command. |
| R11 | The request records `application_version` and `locale` when it is opened. | The design's context panel shows the version the user was on; nothing else records it per user. | Showing the instance's current version: the same on every row, useless. |
| R12 | The queue is a query helper, `App\Helpers\SupportQueue`, read by the admin view model, the admin API and the MCP tool. It sorts and filters age on `created_at`. Filters travel in the query string. | View models end in Blade only (`CLAUDE.md`); a filtered list is the good reason `code-style.md` allows for query strings. | The API and MCP reading the view model. |
| R13 | The user filter lists only users who have at least one request. | An instance can hold thousands of accounts. | Every user: an unusable select. |
| R14 | Two notifications: `SupportRequestReceived` (copy of the user's own request) and `SupportReplySent`. Both implement `HasEmailType`, carry the request page link and say to answer there (FR-014). | Matches `app/Notifications`; the account journal records them. | Mailables: the project has none. |
| R15 | User acts go to the user's journal through `LogUserAction`; administrator replies and status moves go to `LogAdministratorAction`. Notes are not logged; the thread is their record. | Two journals already separate who did what to an account. | One shared log: `AdministratorLog` explains why that is forbidden. |
| R16 | No flag. The user's Support area is absent when the instance has no active administrator (FR spec edge case), checked by one query in a view model and in the entry action. | A flag hides unfinished work; this ships finished. | `flag:support`: dies at release and adds nothing. |
| R17 | The user screens share a new `x-support.page` shell. Its drawer and the settings drawer now render one `x-nav-drawer`. | `components.md` extracts markup carrying a contract at the second file. | A third copy of the drawer. |
| R18 | Docs: `resources/docs/api/32-support-requests.php`, `33-support-administration.php`, MCP docs updated from the tool list, one portal guide in `docs/portal/en/10-your-account-and-security`, and an entry in `docs/FEATURES.md`. | "Proper docs" in the request; each surface already has its home. | A separate support manual. |
| R19 | Outbound webhooks are out of scope. | The application has no outbound webhooks yet; principle X's clause has nothing to plug into. | Building the webhook layer here. |
