# Research: Stripe status in the admin space

| # | Decision | Rationale | Rejected |
| --- | --- | --- | --- |
| R1 | The check is an action, `CheckStripeConnection`, run by the controller on every GET and handed to the view model, as `SearchEngineController` does. "Check again" is a link to the same screen. | `CheckTelegramWebhook` and `CheckSearchEngine` are the precedents for questioning an outside service and changing nothing (FR-011). | A cached status: a stale answer is what the screen exists to remove. |
| R2 | One action returning an array shape: each key set or not and its mode, whether the modes disagree, the environment warning, then the connection and the endpoints. No interface, no value object. | The shape `CheckSearchEngine` returns. | A `StripeHealth` object: more files than logic. |
| R3 | One call answers both questions: `GET https://api.stripe.com/v1/webhook_endpoints?limit=100` with the secret key, through Laravel's HTTP client, `timeout(3)` and `connectTimeout(2)`. 200: the key is accepted and the endpoints are read. 401: the key is refused. 403: the key is accepted but restricted and may not read endpoints (spec edge case). A connection error or timeout: unreachable, with the message. | Cashier's client is `stripe-php`, which has no per request timeout and waits up to 80 seconds by default. Setting its timeout globally would also shorten checkout. `Http::fake()` tests every branch. | Two calls (`/v1/account` then endpoints): twice the time for no extra answer. The SDK's `webhookEndpoints->all()`: no timeout. |
| R4 | An endpoint is this instance's when its `url` equals `route('cashier.webhook')`. The required kinds are `config('cashier.webhook.events')`. An enabled endpoint whose `enabled_events` holds `*` covers every kind. A kind is missing when no enabled endpoint of this instance covers it. Each missing kind is worded with what goes wrong without it, from a fixed list in the view model taken from `docs/STRIPE.md`. Endpoints at other addresses are counted but their address is not shown. | FR-008 and the spec's edge cases. The list in `config/cashier.php` is what `cashier:webhook` would register, so the screen and the command agree. | Matching on the host only: a staging copy on the same host with another path would pass. |
| R5 | The catalogue is read through `StripeCatalogue::offers()` and `isAvailable()`, and only when R3 reached Stripe. When Stripe is unreachable the screen says the catalogue was not read rather than wait on the SDK. The kinds without a price are `OfferKindEnum::cases()` minus the kinds in the offers. On a warm cache this costs no call. On a cold cache it is one SDK call with no timeout of its own, the same call every pricing screen makes. | The catalogue rules (tag, product tag, billing cycle) live in one place and stay there. **FR-010 is not strictly met on a cold cache**: Stripe answered the bounded call a moment earlier, so a hang there is unlikely but not excluded. Tracked in the plan's Complexity Tracking. | A second reader with a timeout: two copies of the rule. A global `stripe-php` timeout: it would also cut checkout short. Reading the cache only: on a cold cache the screen could not tell an unreadable catalogue from one not read yet (US1.7). |
| R6 | `StripeCatalogue` writes a second cache key, `stripe_offers_read_at`, beside the catalogue, with the same lifetime, and exposes `readAt(): ?CarbonImmutable`. `ReloadStripeCatalogue` calls `forget()` (which forgets both keys) then `isAvailable()`. | User Story 3.1 needs the time, and the catalogue cache holds none. A failed read caches nothing today, so after a failed reload every pricing screen keeps behaving as it does when the catalogue is unreadable (User Story 3.3). | A table or an instance setting for one timestamp. |
| R7 | `ReloadStripeCatalogue` takes the administrator, logs `AdministratorActionEnum::StripeCatalogueReloaded` with the number of offers read, and returns whether the catalogue could be read. The controller flashes one of two sentences. No `password.confirm`, no confirmation modal: nothing is destroyed and nothing about how the instance behaves changes. | FR-012 and the spec's assumption. The shape of `StartSearchIndexRebuild`. | Logging from the controller. |
| R8 | Access counts follow `Account::accessKind()` in SQL, in its order, over every account: an account with a paid `stripe_orders` row is a purchase made once; otherwise one with `access_granted_at` is a grant; otherwise one with a valid subscription (Cashier's `active()`, `onTrial()` or `onGracePeriod()` scopes, which is what `subscribed()` reads) is counted by the subscription's kind; every other account holds none. | The same precedence as the model, and Cashier's own scopes rather than the status rules spelled again, so the admin account screen and this one never disagree about one account. | Loading every account and calling `accessKind()`: one query per account. |
| R9 | A subscription's kind is the `kind` stored on its most recent `payments` row (`stripe_subscription_id`). One with no payment yet, or a null kind, is counted as "kind not known". Its state comes from Cashier's scopes: `onGracePeriod()` is cancelled but running, `pastDue()` is waiting on a failed payment, `active()` without the grace period is active. Ended ones are not counted. `AppServiceProvider` calls `Cashier::keepPastDueSubscriptionsActive()`, so `active()` takes in `past_due` (the account keeps its access while Stripe retries); the active count excludes `past_due` explicitly so the three never overlap. | FR-019 forbids asking Stripe, and the catalogue needs Stripe when its cache is cold. `RecordPayment` already stored the kind at payment time. | `StripeCatalogue::kindOfSubscription()`: reaches Stripe on a cold cache. |
| R10 | Payments: one grouped query on `payments` for `billed_at` in the current and the previous calendar month in `config('app.timezone')`, by currency and `kind`, with `count`, `sum(total)`, `sum(tax)`. Refunds and disputes: `stripe_events` rows of type `charge.refunded` and `charge.dispute.created` in the last 30 days. | FR-017 and FR-018 as clarified. `HandleStripeEvent` deletes the row of a confirmation it did not act on, so these rows are exactly the full refunds and disputes that ended access. | Reading `stripe_orders` statuses: misses subscriptions. |
| R11 | Amounts are formatted per currency with the money formatter the account billing screens already use, never summed across currencies. Counts go through `trans_choice()`. | FR-017, the counted phrase rule. | Formatting in Blade. |
| R12 | Confirmations received: one grouped query on `stripe_events` for the last 30 days by `type`, with the count for 7 and 30 days, plus the newest row. Empty reads as one sentence that says none arrived, never that any was lost. | FR-009 and User Story 2.5. Rows are pruned after 30 days, so 30 is the honest window. | Longer windows: the rows do not exist. |
| R13 | Key modes come from the prefix: `pk_test_`, `sk_test_`, `rk_test_` are test, `pk_live_`, `sk_live_`, `rk_live_` are live, anything else is "not recognised". The environment warning compares the secret key's mode with `app()->isProduction()`. Values are never returned by the action, only `set` and the mode. | FR-003, FR-004 as clarified. A test asserts no key value appears in the action's result or the rendered page. | Showing the last four characters: FR-003 forbids any part. |
| R14 | On a self hosted instance (`config('monica.self_hosted')`) the controller runs nothing and the view model returns the one sentence: no key is read, no call is made, no figure is counted. On a hosted instance with no secret key, only the Stripe call and the catalogue are skipped: the keys block names what is missing, the connection reads "not configured", and the figures and confirmations are still shown. | FR-002, FR-003, FR-019 and the spec's edge case. A test asserts no HTTP request was sent in both cases. | Hiding the navigation entry: the constitution forbids a feature on one deployment only. |
| R15 | No flag and no policy. Opening the screen writes nothing to the administrator log. | It ships finished and the `administrator` middleware is the only rule. | Logging every view. |

## Not confirmed

The response fields of R3 and R4 (`data[].url`, `data[].status`, `data[].enabled_events`, the 403
shape for a restricted key) come from Stripe's public documentation, not from a live call. The
plan's last step checks them against a test account. That `stripe_events` rows are deleted when not
acted on was read in `app/Listeners/HandleStripeEvent.php`; that the account billing screens share a
money formatter the admin screen can reuse is assumed and checked in step 3.
